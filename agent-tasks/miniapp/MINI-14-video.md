# MINI-14: Видео обхода

## Цель
Загрузка одного глобального видео, которое засчитывает `submit`.

## Контекст
- **Источник:** `PLAN_FRONTEND_MINIAPP.md`, раздел 3.5 (видео), раздел 2.8 (правило 3 — глобальное видео для submit), фича MINI-14
- **Бэкенд:** 🟡 частично — принимает только `video/mp4` (BE-10 должен разрешить `video/quicktime`), без лимита размера на клиенте (сервер тоже не ограничивает пока)

## Зависимости
- MINI-11. 🟡 BE-10 нужен для нормальной работы с `.MOV` с iPhone (до него — обход на фронте). Надёжность больших файлов — BE-20 (multipart, P2, второй этап).

## Требования

### Экран `/reports/:id/video`
Запись или выбор (`<input type="file" accept="video/*" capture="environment">`), проверка типа и размера, подсказки («до 3 минут», «Наиболее совместимый» для iPhone), загрузка с процентами, Wake Lock, предупреждение «не закрывайте», замена видео (новое загружается, старое остаётся в БД до BE-12 — фронт показывает **последнее**).

### Критичное правило — должно быть глобальным
Видео **обязательно** грузится с `sectionId = null` и `kind = 'VIDEO'` — иначе `submit` его не засчитает (правило 3 из раздела 2.8: сервер ищет `report_media` с `section_id IS NULL`, `kind = 'VIDEO'`, `status IN ('pending','ready')`).

### Проблема `.MOV` с iPhone
iPhone по умолчанию отдаёт `.MOV` (`video/quicktime`, часто HEVC), бэкенд принимает только `video/mp4`. Варианты по убыванию правильности (из плана, раздел 3.5):
- (а) BE-10 разрешает `video/quicktime` на бэкенде, перекодировка — задача будущего ffmpeg-воркера (которого ещё нет);
- (б) временно грузить `.MOV` с `contentType: video/mp4` (контейнеры совместимы — ISO BMFF), но HEVC не проиграется у части покупателей на Android;
- (в) подсказка в UI: «Камера → Форматы → Наиболее совместимый».
**Для MVP выбрано (а) + (в).** Не переоткрывать выбор и не реализовывать (б) по собственной инициативе — зависит от решения, принятого в бэкенд-доработке BE-10. Перекодировка в браузере через ffmpeg.wasm **не рассматривается** — десятки секунд на минуту видео, сотни МБ памяти.

### Размер и постер
Видео 2–3 минуты в 1080p — 200–600 МБ. Лимит на клиенте: предупреждение от 300 МБ, отказ от 1 ГБ (ориентир серверного лимита BE-10). Подсказка «до 3 минут». Постер — первый кадр через `<video>` + canvas, грузится тем же способом, что миниатюра (вторым presigned PUT) — **только при наличии бэкенд-фичи B-39**, до неё — локально.

### Надёжность
Одиночный PUT на сотни МБ по мобильной сети — самое хрупкое место. До BE-20 (multipart, второй этап): видео в очереди отдельно (уже обеспечено MINI-11 — видео не параллелится с фото), `navigator.wakeLock.request('screen')` (если доступен), явное предупреждение с процентами. После обрыва — закачка **с начала** (докачка невозможна без multipart).

## Acceptance Criteria
- [ ] видео с Android (`mp4`) загружается и появляется в `globalMedia` со статусом `pending`
- [ ] видео уходит с `sectionId = null` и `kind = VIDEO`, так что `submit` его засчитывает
- [ ] файл больше лимита отклоняется до загрузки
- [ ] `.MOV` с iPhone обрабатывается по выбранной стратегии (BE-10 + UI-подсказка) и не падает с непонятной ошибкой
- [ ] прогресс и повтор после обрыва работают (с начала, до BE-20)

## Gotchas
1. **Видео обязательно глобальное** (`sectionId=null`, `kind=VIDEO`) — если привязать к секции, `submit` его не увидит (гоча 5 из плана).
2. **`.MOV`/HEVC не проигрывается на части Android** — принятый риск до появления ffmpeg-воркера, не решать самостоятельно перекодировкой в браузере.
3. Докачка с середины невозможна до BE-20 — после разрыва видео грузится заново целиком.
4. Постер зависит от B-39 (как и миниатюры фото в MINI-12) — без него только локальный превью-кадр.

## Промпт для агента

```
2. Загрузка строго с sectionId=null и kind='VIDEO' (критично для submit!)

```
