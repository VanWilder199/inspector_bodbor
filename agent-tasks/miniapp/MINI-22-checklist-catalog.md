# MINI-22: Серверный справочник чеклиста и медиа-лимиты

## Цель
Убрать локальный хардкод чеклиста, перейти на серверный справочник.

## Контекст
- **Источник:** `PLAN_FRONTEND_MINIAPP.md`, раздел 5 BE-5, BE-10, фича MINI-22
- **Бэкенд:** ❌ **БЛОКЕР** — эндпоинта `GET /inspector/catalog/checklist` нет вообще; 🟡 BE-10 (лимиты медиа) частично

## Зависимости
- MINI-09, MINI-17, **BE-5** (блокер)

## ⚠️ Блокер
Нет эндпоинта. Предлагаемый контракт (раздел 5, BE-5):
```json
{
  "version": 1,
  "sections": [
    {
      "sectionKey": "EXTERIOR", "title": "Кузов",
      "instruction": "Осмотрите кузов при дневном свете с 4 сторон…",
      "items": [
        { "itemKey": "geometry", "title": "Геометрия кузова", "hint": "…", "required": true, "photoRequiredOn": "BAD", "orderNo": 1 }
      ]
    }
  ]
}
```
Путь — под `/inspector/**` (не `/catalog/**`, который попал бы в JWT-цепочку покупателя), чтобы работал initData. До появления этого эндпоинта чеклист хардкодится на фронте в `apps/inspector/src/catalog/checklist.ts` (сделано в MINI-09, временный `ITEM_LABELS` из `packages/ui/src/report/catalog.ts`, 42 ключа).

## Требования (на момент появления BE-5)
Загрузка `GET /inspector/catalog/checklist` (кеш по `version` в `localStorage`), замена `apps/inspector/src/catalog/checklist.ts` на данные с сервера. Обязательность пунктов (`required`) и фото (`photoRequiredOn`) в чек-листе готовности (MINI-17) становится **блокирующей** (сейчас — предупреждение). Лимиты медиа — из BE-10 (`GET /inspector/catalog/media-limits` или встроено в ответ BE-5): `{ photoMaxBytes, videoMaxBytes, allowedContentTypes }`.

## Acceptance Criteria
- [ ] пункты секций, подписи и подсказки приходят с сервера
- [ ] неизвестный локальный `itemKey` из старого черновика не отправляется (с предупреждением пользователю)
- [ ] чек-лист готовности блокирует отправку при неоценённом `required`-пункте (замена предупреждения из MINI-17 на блокер)
- [ ] до появления BE-5: фронт продолжает работать на хардкоде из MINI-09, этот экран/логика не влияет на прод

## Gotchas
1. **Эндпоинта нет вообще** — работать на моках, контракт — предположение плана.
2. Переключение с предупреждения на блокер в чек-листе MINI-17 — изменение поведения существующего экрана, делать аккуратно через фичефлаг/наличие данных с сервера (если справочник не загрузился — оставаться в режиме предупреждения, не блокировать всех пользователей из-за сбоя одного запроса).
3. Старые локальные черновики могут содержать `itemKey`, которого больше нет в серверном справочнике (после смены версии) — не терять данные молча, предупреждать.

## Промпт для агента
```
Реализуй переход на серверный справочник чеклиста согласно MINI-22-checklist-catalog.md.

ВАЖНО: эндпоинт GET /inspector/catalog/checklist (BE-5) ПОКА НЕ СУЩЕСТВУЕТ на бэкенде. Работай на MSW-моках по предполагаемому контракту из раздела 5 BE-5 плана, явно помечая его как предположение:
1. Загрузка справочника с кешем по version в localStorage
2. Замена apps/inspector/src/catalog/checklist.ts (хардкод из MINI-09) на данные с сервера, с graceful fallback на хардкод, если запрос справочника не удался
3. В чек-листе готовности (MINI-17): required-пункты и photoRequiredOn становятся блокирующими, НО только когда справочник реально загружен с сервера — если фронт работает на фолбэк-хардкоде, оставить их предупреждениями (как сейчас)
4. Лимиты медиа из BE-10: GET /inspector/catalog/media-limits (или поле в ответе BE-5), применить в MINI-12/MINI-14 для клиентской валидации размера
5. Обработка неизвестного itemKey в старом локальном черновике — предупреждение, не потеря данных

Проверь acceptance criteria на моках, убедись что graceful fallback работает, если сервер недоступен.
```
