> **Правило для агентов: ничего не запускать.** Не поднимать dev-серверы (`npm run dev:*`, `vite`, `vite preview`), туннели, бота (`python bot/...`, `docker compose up`), не открывать браузеры (в том числе headless Chrome/Firefox ради скриншотов), не стартовать заглушки бэкенда и любые фоновые процессы, не ходить `curl` на локальные порты. ## Контекст

Mini App подборщика — отдельное приложение `frontend/apps/inspector` на `@telegram-apps/telegram-ui` + `@telegram-apps/sdk-react`, **без MUI**. Рядом — тонкий бот `bot/` (aiogram 3): только `/start`, кнопка открытия Mini App, `/new_report`, без FSM и без обращений к API/БД. Все уведомления подборщику шлёт бэкенд напрямую через Bot API, не бот.

На бэкенде Mini App опирается на блоки из `IMPLEMENTATION_PLAN.md`:
- **Блок 0** (Фундамент — миграции, DTO, `GlobalExceptionHandler`) — готово;
- **Блок 3** (Telegram HMAC авторизация подборщика, `InspectorService`) — готово, основной флоу работает;
- **Блок 5** (`AvByParser`, `CarService.findOrCreateByUrl`) — готово, с оговорками по валидации URL (BE-19);
- **Блок 6** (S3, presigned PUT/confirm) — готово, но без владельческих проверок (BE-9) и без публичного endpoint для presigner (BE-17);
- **Блок 7** (создание и редактирование отчётов, 7 секций, ЛКП, submit) — готово по основному флоу, с валидационными ограничениями, которые мешают автосохранению (BE-14);
- **Блок 4** (уведомления) — в коде сейчас только email/лог (`NotificationSender` → `NotificationSenderImpl`, `UniSenderClient` в разработке, судя по текущему git-статусу репозитория); канала `TELEGRAM` нет (BE-16);
- **Блок 9** (платежи/выплаты) косвенно нужен для уведомления о продаже подборщику — этого вызова сейчас нет (BE-16, строка «Продажа»).

## Зафиксированные решения (не переоткрывать, не предлагать альтернативы)

1. Mini App и API — **один origin** (`https://app.site.by`, nginx проксирует `/api/` → `api:8080`). CORS на API не нужен (BE-1 не нужен в текущей архитектуре).
2. CORS на **S3-бакете** обязателен — PUT по presigned URL идёт напрямую в S3, другой origin.
3. Роутер — `BrowserRouter`, **не `HashRouter`**, база — корень `app.site.by`.
4. Сервер — источник истины, `localStorage` — черновик со флагами `dirty` на уровне секций/ЛКП/заключения.
5. **MVP (решение 2026-09-29, п. 3):** очередь загрузок — **в памяти** (не IndexedDB), пока Mini App открыт. IndexedDB, восстановление очереди после закрытия, `persistQueryClient` — второй этап (MINI-21, MINI-23).
6. Все фото перекодируются в JPEG на клиенте (HEIC, размер, приватность EXIF/GPS).
7. Имя файла для S3 генерирует клиент (`<uuid>.jpg`), пока это не делает бэкенд (BE-9).
8. Типы API — вручную в `apps/inspector/src/api/types.ts`, до springdoc (BE-18).
9. Моки — через MSW, контракт из раздела 5 плана, переключаются флагом `VITE_API_MOCKS`.
10. UI — `@telegram-apps/telegram-ui`, Mini App выглядит нативно для Telegram (не shadcn, как у покупателя/админки).
11. Уведомления — все события в Telegram; верификация, бан, публикация отчёта, формирование/оплата выплаты — дополнительно на email.

## Легенда статусов бэкенда

- ✅ **готово** — эндпоинт есть и работает без существенных оговорок
- 🟡 **частично** — эндпоинт есть, но с ограничениями/дырами, которые влияют на фичу
- ❌ **нет** — эндпоинта или контракта нет вообще, нужна бэкенд-разработка

## Нерешённые вопросы / явные риски из плана (не придумывать решение, ждать бэкенд или продуктовое решение)

1. **`panelId` для ЛКП взять неоткуда** — UUID панелей генерируются миграцией и разные в каждой базе (локально/тест/прод). Без BE-6 (`GET /inspector/catalog/paint-panels` или приём `panelCode` вместо `panelId`) MINI-15 не может сохранять замеры на сервер.
2. **Confirm-upload не идемпотентен** — повторный вызов после таймаута создаёт дубль фото. Временное смягчение на фронте (перечитать `GET` перед повтором) есть, настоящее исправление — BE-9 (`UNIQUE(s3_key)`).
3. **Удалить медиа нельзя** (BE-12 не реализован) — ошибочное фото навсегда остаётся в отчёте. До BE-12 UI обязан показывать подтверждение перед загрузкой, а не после.
4. **`.MOV` с iPhone (`video/quicktime`, HEVC)** — бэкенд принимает только `video/mp4`. Решение для MVP выбрано (BE-10 разрешает `quicktime`, перекодировка — в будущем ffmpeg-воркер), но ffmpeg-воркер не реализован, и часть покупателей на Android может не воспроизвести HEVC. Это принятый риск, а не решённая проблема.
5. **S-22 (принятый риск, зафиксирован в MINI-13):** клиентская миниатюра может не совпадать с полным фото (подмена в сетке), потому что миниатюра и полное фото — разные загрузки и сервер их не связывает до B-39. Вариант принят как временный техдолг (B-97), фронт ничего не чинит сам.
6. **Одиночный PUT большого видео по мобильной сети** — главный риск надёжности до BE-20 (multipart upload). После разрыва закачка начинается с начала.
7. **S3 в локальной разработке** — presigned URL на `http://localhost:9000` недостижим с телефона по HTTPS (mixed content). Нужен BE-17 (публичный endpoint для presigner) + туннель для MinIO; без этого MINI-04/MINI-10 проверяются только в десктопном браузере с мок-окружением.
8. **Причина бана/удаления/доработки недоступна подборщику через API** — уходит только в уведомление. BE-8 должен добавить `lastModeration` в `ReportDto`, до этого Mini App показывает «причина — в сообщении от бота».

## Формат задач

Каждый файл содержит:
- **Цель** — что делает фича
- **Контекст** — ссылка на раздел исходного плана
- **Зависимости** — какие MINI/BOT-задачи и бэкенд-блоки должны быть готовы

- **Gotchas** — ловушки из плана, включая нерешённые вопросы
- **Промпт для агента** — готовый текст для исполнителя

## Как использовать
