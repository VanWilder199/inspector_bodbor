# MINI-12: Обработка фото — HEIC → JPEG, ресайз, миниатюры

## Цель
Все фото уходят на сервер как JPEG разумного размера, без утечки EXIF/GPS.

## Контекст
- **Источник:** `PLAN_FRONTEND_MINIAPP.md`, раздел 3.5 (обработка фото и видео), решение 6 (все фото перекодируются в JPEG), фича MINI-12
- **Бэкенд:** не нужен для обработки. Загрузка миниатюры вторым объектом — отдельная бэкенд-фича **B-39** (не входит в раздел 5 этого плана; см. `PLAN_MEDIA_THUMBNAILS.md`), не блокер.

## Зависимости
- MINI-11

## Требования

### `src/media/processImage.ts` (Web Worker + `OffscreenCanvas`, где доступно; иначе main thread)
1. Выбор файла: `<input type="file" accept="image/*" capture="environment">` для камеры, без `capture` для галереи, с `multiple`.
2. **HEIC**: определяется по `file.type` (`image/heic`, `image/heif`) или по расширению, если `type` пустой. Сначала `createImageBitmap(file)` (Safari 17+/iOS WebView декодируют сами); если не вышло — lazy-import `heic2any` (wasm, ~1 МБ, грузится только при необходимости, не в основной бандл).
3. **Ориентация**: `createImageBitmap(file, { imageOrientation: 'from-image' })` — EXIF-поворот применяется к пикселям.
4. **Ресайз**: длинная сторона до **2560 px**, меньшие фото не увеличиваются.
5. **Кодирование**: JPEG `quality 0.82`. Итог обычно 0,5–1,5 МБ вместо 3–8 МБ. `contentType` всегда `image/jpeg`.
6. **EXIF, включая GPS, не переносится** — canvas не переносит метаданные (плюс для приватности).
7. **Миниатюра** 480 px (JPEG) — для очереди/превью на этом устройстве. Загрузка миниатюры вторым presigned PUT (`thumbUploadUrl`/`thumbS3Key`) — только при наличии бэкенд-фичи B-39; до неё миниатюра **только локальная**.
8. **Память**: файлы обрабатываются строго по одному, после каждого — `bitmap.close()` и `canvas.width = canvas.height = 0` (iOS WebView падает при множестве больших canvas подряд).

## Acceptance Criteria
- [ ] HEIC с iPhone загружается как `image/jpeg`, вертикальное фото не повёрнуто
- [ ] фото 12 Мп на 4–8 МБ становится ≤ 1,5 МБ
- [ ] 20 фото подряд не роняют WebView на iPhone среднего класса
- [ ] в итоговом JPEG нет EXIF GPS
- [ ] `heic2any` не попадает в основной бандл (проверить отчёт сборки)
- [ ] при наличии B-39 миниатюра 480px грузится вторым presigned PUT, confirm отправляет `thumbS3Key`, `width`, `height` — при отсутствии B-39 миниатюра остаётся только локальной

## Gotchas
1. **`heic2any` — lazy import**, иначе раздувает основной бандл на ~1 МБ для всех пользователей, даже без HEIC-фото.
2. **Строго последовательная обработка** — параллельная обработка нескольких больших canvas валит WebView на iOS.
3. Миниатюра второй загрузкой — зависит от бэкенд-фичи B-39, которая **не входит в раздел 5** этого плана и не гарантирована в ближайших итерациях; код должен работать и без неё (чисто локальная миниатюра).
4. Эта задача — чистая клиентская логика, моков не требует, но нужны тестовые файлы-фикстуры (HEIC, EXIF с GPS, разные ориентации).

## Промпт для агента
```
Реализуй обработку фото согласно MINI-12-photo-processing.md:

1. src/media/processImage.ts в Web Worker (OffscreenCanvas, fallback на main thread)
2. Определение HEIC (file.type или расширение), createImageBitmap с fallback на lazy heic2any
3. Коррекция ориентации через imageOrientation: 'from-image'
4. Ресайз до 2560px по длинной стороне (без увеличения меньших), JPEG quality 0.82
5. Генерация миниатюры 480px
6. Строго последовательная обработка: bitmap.close() и сброс canvas после каждого файла
7. Проверка: EXIF GPS не переносится в итоговый JPEG
8. Интеграция в постановку в очередь загрузок (MINI-11)
9. Подготовь тестовые фикстуры: HEIC-файл, JPEG с EXIF GPS, фото с разной ориентацией (EXIF orientation 1-8)

Если бэкенд-фича B-39 (вторая presigned-загрузка миниатюры) не реализована — миниатюра используется только локально, не пытайся угадать её контракт.

Проверь все acceptance criteria, особенно отсутствие heic2any в основном бандле (анализ сборки) и память при 20 фото подряд.
```
