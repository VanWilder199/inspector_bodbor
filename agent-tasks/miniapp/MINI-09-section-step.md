# MINI-09: Шаг секции — чеклист, оценки, итог, автосохранение

## Цель
Заполнение одной секции отчёта с надёжным автосохранением, несмотря на строгую валидацию бэкенда.

## Контекст
- **Источник:** `PLAN_FRONTEND_MINIAPP.md`, раздел 2.6 (`PUT .../sections/{sectionId}`), раздел 3.3 (правила автосохранения), фича MINI-9
- **Бэкенд:** 🟡 частично — эндпоинт работает, но с ограничениями, которые ломают наивное автосохранение (см. ниже). BE-5 (справочник пунктов) и BE-14 (ослабление валидации) — желательные улучшения, не блокеры.

## Зависимости
- MINI-08

## Требования

### Экран `/reports/:id/section/:sectionKey`
Инструкция секции, список пунктов (временно — хардкод `ITEM_LABELS` + локальная раскладка по секциям в `apps/inspector/src/catalog/checklist.ts`, до BE-5/MINI-22), у каждого пункта сегмент OK/WARN/BAD (цвет+иконка+текст) и комментарий (**обязателен на фронте** при WARN/BAD, бэкенд этого не требует), поле «Итог секции» (`summary`), индикатор «Сохранено / На устройстве / Ошибка».

### Контракт (раздел 2.6)
Тело: `{ summary, items: [{ itemKey, status, comment }] }`.
- `summary` — `@NotBlank` на бэкенде;
- `items` — `@NotNull @Valid`, `itemKey` — свободная строка (не сверяется со справочником, дубли не запрещены до BE-5), `status` `@NotNull` (`OK|WARN|BAD`), `comment` — опционален.

**Семантика — полная замена (replace-all)**: `UPDATE summary` → `DELETE` всех пунктов секции → `INSERT` пришедших. Для автосохранения это означает:
- **всегда отправлять полный список пунктов секции**, а не только изменённый — пункт, которого нет в запросе, удаляется;
- запрос идемпотентен — повтор после сетевой ошибки безопасен;
- **для одной секции в полёте — максимум один запрос**, новые изменения объединяются в следующий (last write wins), иначе более поздний ответ на более старый запрос затрёт новые данные.

### Ограничения валидации (пока без BE-14)
1. **Без `summary` секцию не сохранить** (`@NotBlank`). До ввода итога — отметки живут только локально, индикатор показывает «сохранено на устройстве», не ошибку.
2. **У каждого отправляемого пункта обязателен `status`.** Неоценённые пункты просто не отправляются (не отправлять `null`/`undefined` status).
3. **Пустой `items: []` — вероятно, `500`.** Пустой список никогда не отправляется.

### Правила автосохранения (раздел 3.3)
- debounce 1,5 с после изменения;
- flush при уходе с шага (BackButton, MainButton, переход по хабу), `deactivated`, `visibilitychange: hidden`;
- `409 REPORT_NOT_EDITABLE` → черновик сбрасывается, отчёт перечитывается и открывается только на чтение;
- `404 REPORT_NOT_FOUND` → черновик удаляется, «Отчёт удалён».

## Acceptance Criteria
- [ ] без `summary` запрос не уходит, индикатор показывает «На устройстве»
- [ ] при изменении одного пункта уходит `PUT` со **всеми** оценёнными пунктами секции
- [ ] пустой список пунктов никогда не отправляется
- [ ] быстрые изменения не создают параллельных `PUT` одной секции — последнее состояние доходит до сервера (last write wins)
- [ ] уход с шага (BackButton/MainButton) дожидается flush или оставляет `dirty` при офлайне
- [ ] `409 REPORT_NOT_EDITABLE` переводит экран в режим чтения
- [ ] после перезагрузки данные совпадают с сервером (перечитать и сравнить)

## Gotchas
1. **`summary` обязателен при каждом сохранении** — автосохранение до ввода итога только локальное, это нормально и ожидаемо, не баг.
2. **Полная замена, не патч** — не отправлять частичный список пунктов.
3. Пустой `items: []` вероятно даёт `500` — защититься на уровне кода запроса, а не только UI.
4. Одна секция — один запрос в полёте: нужна явная блокировка (например, через ref/флаг «запрос идёт»), а не просто debounce.
5. `itemKey` — свободная строка до BE-5, дубли технически возможны на бэкенде — локальный справочник должен гарантировать уникальность ключей на фронте сам.

## Промпт для агента
```
Реализуй шаг секции согласно MINI-09-section-step.md:

1. /reports/:id/section/:sectionKey: инструкция, список пунктов из apps/inspector/src/catalog/checklist.ts (хардкод до BE-5), сегмент OK/WARN/BAD с комментарием (обязателен на фронте при WARN/BAD), поле «Итог секции»
2. Автосохранение: PUT всегда с ПОЛНЫМ списком оценённых пунктов (replace-all семантика бэкенда), debounce 1.5с, flush при уходе с шага/deactivated/visibilitychange
3. Правило «одна секция — один запрос в полёте»: новые изменения во время запроса помечаются dirty и уходят следующим PUT
4. Не отправлять PUT без summary (пока только локально, индикатор «На устройстве»)
5. Никогда не отправлять items: [] (пустой список)
6. 409 REPORT_NOT_EDITABLE → режим чтения + перечитать отчёт; 404 → удалить черновик, «Отчёт удалён»
7. Индикатор состояния: Сохранено / На устройстве / Ошибка

Проверь все acceptance criteria, особенно «last write wins» при быстрых изменениях и невозможность отправки пустого summary/items.
```
