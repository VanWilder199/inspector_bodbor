# MINI-05: Онбординг — bootstrap, регистрация, ожидание, бан

## Цель
Маршрутизация по статусу подборщика: незарегистрирован → форма регистрации, `pending` → ожидание, `verified` → главный экран, `banned` → заблокирован.

## Контекст
- **Источник:** `PLAN_FRONTEND_MINIAPP.md`, раздел 1.1 (сценарии A, B, C), раздел 2.3 (`GET /inspector/`, `POST /inspector/register`), фича MINI-5
- **Бэкенд:** 🟡 частично — `GET /inspector/` ✅ готово, `POST /inspector/register` 🟡 (слабая валидация, см. ниже)

## Зависимости
- MINI-03. 🟡 BE-4 желателен (без него фронт сам не пропускает пустой email). 🟡 BE-3 — серверная защита (сейчас `pending` технически может создавать отчёты, фронт обязан сам не пускать).

## Требования

### Экраны
- `/` — bootstrap: SDK → `GET /inspector/` → редирект по статусу.
- `/register` — форма react-hook-form + zod: ФИО (предзаполнено из `initData.user.first_name`/`last_name`), телефон с маской `+375`, **email обязателен на фронте** (бэкенд падает в `500`, если его нет — см. Gotchas).
- `/pending` — «Заявка на проверке», статус перезапрашивается при каждом открытии Mini App и при `activated` (plus pull-to-refresh).
- `/banned` — «Аккаунт заблокирован», без действий. Причину бана API не отдаёт (уходит только в уведомление).
- `/profile` — данные `InspectorDto`.
- После успешной регистрации — вызов `requestWriteAccess()` («Разрешить уведомления о модерации»).

### Контракт API (раздел 2.3)
`GET /inspector/` — **строго со слешем**. `200 InspectorDto` или `404 INSPECTOR_NOT_FOUND` (штатный сигнал «нужна регистрация», не ошибка).

`POST /inspector/register`, тело `{ fullName, phone, email }`:
- `fullName` — `@NotBlank`;
- `phone` — только `@NotNull`, **пустая строка проходит** (бэкенд не валидирует формат — фронт обязан сам проверить `+375`);
- `email` — только `@Email`, может быть `null` на уровне валидации, но БД требует `NOT NULL` → без email получится **`500 INTERNAL_SERVER_ERROR`**, не `400`. Фронт делает email обязательным сам.

Ответ `200 InspectorDto`, `status: "pending"` (не `201`).
`409 INSPECTOR_ALREADY_REGISTERED` — трактуется как успех → перезапрос `GET /inspector/`.

### Что фактически разрешает бэкенд по статусам (таблица из раздела 2.3)
| Статус | Бэкенд разрешает | Mini App должен разрешать |
|---|---|---|
| не зарегистрирован | только `register`; `/inspector/reports/**` → `404`. Но `/inspector/media/**` **работает** (нет проверки подборщика) | только регистрация |
| `pending` | всё (создание, редактирование, отправку — проверяется только `banned`) | экран ожидания, профиль. Мастер закрыт **на фронте** (BE-3 не реализован) |
| `verified` | всё | всё |
| `banned` | нельзя создать отчёт (`403 INSPECTOR_BANNED`), но **можно** читать/редактировать/отправлять существующие (статус не проверяется) | экран «заблокирован», без доступа к существующим отчётам |

## Acceptance Criteria
- [ ] `404 INSPECTOR_NOT_FOUND` ведёт на `/register`, `pending` — на `/pending`, `verified` — на `/reports`, `banned` — на `/banned`
- [ ] после успешной регистрации открывается `/pending` без повторного запроса
- [ ] `409 INSPECTOR_ALREADY_REGISTERED` трактуется как успех (перезапрос профиля)
- [ ] ошибки `errors[]` показываются у полей
- [ ] пользователь `pending` не может попасть в `/reports/new` и мастер, даже по прямой ссылке или `startapp`
- [ ] при возврате в Mini App (`activated`) статус перечитывается
- [ ] email обязателен на форме, даже если бэкенд технически пропустит `null` (и упадёт в `500`)

## Gotchas
1. **Регистрация без email → `500`, не `400`** — БД `NOT NULL`, валидация на уровне DTO это не ловит. Фронт обязан требовать email сам, до BE-4.
2. **`pending` фактически может создавать и отправлять отчёты на бэкенде** — ограничение целиком на фронте, до BE-3.
3. **`banned` может редактировать существующие отчёты через API** — Mini App сознательно не даёт доступа из UI, до BE-3.
4. Ответ регистрации — `200`, не `201`.
5. Причина бана недоступна через API — показывать «подробности — в сообщении от бота», не выдумывать текст.

```
Реализуй онбординг подборщика согласно MINI-05-onboarding.md:

1. /: bootstrap — GET /inspector/ → редирект по статусу (404→/register, pending→/pending, verified→/reports, banned→/banned)
2. /register: форма react-hook-form + zod, ФИО предзаполнено из initData.user, телефон с маской +375, email обязателен на фронте (!), POST /inspector/register
3. /pending: перезапрос статуса по activated и pull-to-refresh

7. 409 INSPECTOR_ALREADY_REGISTERED → трактовать как успех, перезапросить GET /inspector/
8. Клиентский гейт: pending и banned не попадают в мастер создания/редактирования отчётов, даже по прямой ссылке/startapp

Проверь все acceptance criteria, включая обязательность email на форме и невозможность попасть в мастер для pending/banned.
```
