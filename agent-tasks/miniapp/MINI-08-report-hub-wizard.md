# MINI-08: Хаб отчёта и каркас мастера

## Цель
Загрузка отчёта, модель черновика, навигация по шагам мастера.

## Контекст
- **Источник:** `PLAN_FRONTEND_MINIAPP.md`, раздел 2.5 (`GET /inspector/reports/{id}`), раздел 3.3 (черновик и слияние с сервером), фича MINI-8
- **Бэкенд:** 🟡 частично — `GET` работает в любом статусе, но без данных машины, URL медиа и причины доработки (BE-8 — желательное улучшение, не блокер каркаса)

## Зависимости
- MINI-07. 🟡 BE-8 — для шапки (название машины) и показа медиа после перезапуска с другого устройства.

## Требования

### Экран `/reports/:id` — хаб
Шапка: машина (пока из URL отчёта или «Автомобиль» — данных машины в ответе нет до BE-8), статус, список шагов с прогрессом («заполнено / частично / пусто») и индикатором синхронизации.

### Порядок шагов
старт (обязательные фото) → 7 секций **в порядке `orderNo`** из ответа (ЛКП включает замеры) → видео → заключение → проверка.

### Контракт `GET /inspector/reports/{reportId}` (раздел 2.5)
Работает в **любом** статусе (владелец, не удалён). Ключевые нюансы ответа:
- **`sectionId` для `PUT .../sections/{sectionId}` берётся только из `sections[].id`**, сопоставление по `sectionKey`. Другого способа нет.
- **Порядок `items` и `media` не гарантирован** (нет `ORDER BY` на бэкенде) — фронт сортирует сам, по порядку справочника.
- **URL медиа нет, только `s3Key`.** Бакет приватный — показать уже загруженные фото на другом устройстве нельзя до BE-8 (presigned GET). Свои недавние загрузки — из памяти (очередь, MINI-11), чужие/старые — заглушка.
- `paintMeasurements[]` содержит `panelCode`, но не `panelId` — отдельная проблема для MINI-15 (BE-6).
- `stopFactors` — `itemKey` всех пунктов со статусом `BAD`, подпись — через `itemLabel()`.
- Причины доработки/удаления в ответе **нет** (лежат в `moderation_log`, недоступны через `/inspector/**` до BE-8).

### Черновик и слияние (раздел 3.3)
Модель `ReportDraft` в zustand с `persist` в `localStorage`, ключ `podbor:draft:<reportId>`, структура — см. раздел 3.3 плана (поля `sections`, `paint`, `conclusion`, `localMediaTags`, у каждой части — `dirty`, `lastSavedAt`, `lastError`). Правило слияния: для каждой части — если локально `dirty = true`, берётся локальная версия и ставится в отправку; иначе — серверная.

`WizardLayout`: шапка с прогрессом шагов и индикатором очереди, MainButton «Далее», BackButton — предыдущий шаг. Режим только для чтения для `pending_review`/`published` (MainButton скрыт). Closing confirmation при `dirty`.

## Acceptance Criteria
- [ ] `sectionId` каждой секции берётся из `GET` по `sectionKey`
- [ ] порядок шагов: старт → 7 секций в порядке `orderNo` → видео → заключение → проверка
- [ ] после перезагрузки Mini App несохранённые локальные правки на месте и помечены `dirty`
- [ ] отчёт `pending_review` открывается только на чтение, MainButton скрыт
- [ ] `404 REPORT_NOT_FOUND` показывает экран «удалён» и чистит черновик
- [ ] при закрытии с `dirty`-данными Telegram спрашивает подтверждение

## Gotchas
1. **`sectionId` только из `GET`**, нельзя сгенерировать или угадать клиентом.
2. **Порядок `items`/`media` не гарантирован бэкендом** — сортировать на клиенте всегда.
3. Данных машины и причины доработки нет в ответе — не придумывать, показывать заглушку/«см. сообщение от бота».
4. `403 REPORT_ACCESS_DENIED` для чужого отчёта, `404 REPORT_NOT_FOUND` для несуществующего/мягко удалённого — разные обработки.
